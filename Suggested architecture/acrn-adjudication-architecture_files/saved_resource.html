00

Design intent

Three decisions shape everything below, and they are worth arguing about before any code is written.

Non-negotiable

The rules engine decides. The language model writes. No AI output ever sets a diagnostic flag, a severity grade, or a classification. Criteria are computed deterministically from coded source facts and are reproducible years later. The model only turns those facts into readable prose that a clinician then edits and signs.

Second: facts are immutable, decisions are versioned. Every clinical value carries provenance back to the system and record it came from. Nothing is overwritten. A late lab result creates a new fact and a case-reopen event, not a silent edit.

Why it mattersPart 11 and GCP inspections ask "what did the reviewer see at the moment they signed?" You can only answer that if the fact set is point-in-time reconstructable.

Third: build for the endpoint, not for pre-eclampsia. Triggers, criteria, form fields, and narrative templates are configuration, not code. Adding a cardiovascular or neonatal endpoint later should mean authoring a new rule set, not forking the application.

Scope disciplineConfigurable does not mean generic. Ship the PE rule set hard-coded in config, prove it, then generalise.
01

System architecture

Event-driven core inside a modular monolith. Not microservices. The workload is a few hundred adjudications per year across a handful of sites, and every service boundary you add is another validation artefact, another deployment to qualify, and another place where the audit trail can fork. One deployable, clean internal module boundaries, one transactional database.

The event bus is what makes the workflow feel automatic: triggers, ingestion completions, rule evaluations, and signatures are all facts published to a durable log that other modules subscribe to.

Case lifecycle

  1. Detect. A standing query over the canonical fact store matches a trigger definition (BP threshold, PE suspicion form, hypertensive delivery, maternal SAE, fetal or neonatal SAE) and emits trigger.detected.
  2. Assemble. The assembler opens a case, defines the clinical window (typically index event minus 14 days through delivery plus 42 days), and pulls every fact in scope. It computes a completeness score and blocks narrative generation until required facts land or are explicitly waived.
  3. Evaluate. The criteria engine runs the pinned rule-set version and writes derived flags with the exact facts that fired each one.
  4. Draft. The narrative service renders prose from the structured timeline plus derived flags, then validates it against the fact set before it is ever shown.
  5. Review. Reviewer A works the case, signs. Workflow routes to Reviewer B blinded to A's answers.
  6. Resolve. Concordant means final. Discordant means committee session, side-by-side, chair records outcome.
  7. Lock. Record frozen, PDF/A rendered, audit chain sealed, artefact filed to the TMF path.

One canonical model, many dumb adapters. Every connector's only job is to fetch, map to FHIR R4 resources with coded terminology, attach provenance, and hand off. No business logic lives in a connector, ever, because connectors get rewritten when vendors change and rules must not.

Rules the pipeline must obey

  • Idempotency by natural key. source_system + source_record_id + version. Re-delivery is a no-op, never a duplicate fact.
  • Provenance on every datum. System, record ID, retrieval timestamp, payload hash, and mapping version. This is what powers the "show me the source" click in the review screen.
  • Units and baselines are computed, not trusted. Convert to UCUM at ingest. Creatinine "doubling from baseline" needs a defined baseline fact, so the assembler resolves and pins it explicitly.
  • Late data reopens or amends. Unsigned case: reopen, re-evaluate, notify assignee of what changed. Signed case: create an amendment record, never mutate the locked one.
  • Manual abstraction is a first-class channel. Flagged visually, attributed to a person, and counted so you can see which source is failing you.
Watch itemThe completeness score is the difference between "automated" and "automatically wrong." Tune it with the data managers before go-live.
03

Rules engine & AI orchestration

Two components, strictly separated, running in a fixed order. The criteria engine is a pure function: canonical facts plus a pinned rule-set version go in, derived flags with evidence pointers come out. Same input, same version, same output, forever. That reproducibility is the entire regulatory argument.

Criteria engine

Rules are authored declaratively (JSON predicates over coded facts) so a clinician can read and approve them without reading code. Each rule carries an ID, a criteria-set citation, an effective date, and an author signature. Rule sets are versioned like protocol amendments: PE-ISSHP-2021.v3. Every adjudication stores the version it was evaluated under.

Narrative service

The model receives a compact JSON payload: the structured timeline, the derived flags, and the evidence that fired them. It never receives raw documents, free-text notes, or identifiers. It returns prose only, against a study-specific template with a fixed section order.

Three gates before a clinician sees a word

  • Numeric echo check. Every number, gestational age, and unit in the draft must exist verbatim in the fact payload. One mismatch, one automatic regeneration, then it fails to a "narrative unavailable" state and the reviewer works from the timeline.
  • Claim containment. The draft may not assert a criterion the engine did not derive. Detected by matching narrative claims to flag IDs.
  • Determinism budget. Temperature near zero, prompt and model version recorded, output hashed into the audit trail alongside the input payload.
Failure is fineA blank narrative is a mild inconvenience. A confidently wrong one is a data integrity finding. Design the fallback first.
Orchestration order

assemble → evaluate criteria → validate completeness → draft narrative → gate → present → human edit → sign → lock

Criteria always run before the narrative. If the engine cannot evaluate, the narrative never generates. The clinician's edits to the narrative are tracked as diffs against the AI draft, so you can report the human edit rate as a quality signal on the model.

Relationships worth stating out loud

  • A pregnancy has many triggers; a trigger opens at most one case, and the assembler merges triggers that fall inside an open window rather than spawning duplicate cases.
  • derived_criterion is written once per evaluation run, never updated. Re-evaluation appends a new set and the case points at the current run.
  • A case has one review per reviewer role. Concordance is computed, not stored as a flag, so the definition can change without a data migration.
  • Everything hangs off audit_event by entity_id, including reads of source documents where regulators expect access logging.
Reconstruction testYou should be able to rebuild the exact review screen a signer saw from case_id plus signed_at. If you can't, the model is wrong.
05

Security, privacy & Part 11

Minimise the PHI you hold

The application never stores names, national IDs, addresses, or dates of birth. Participants are the study subject number only. Ages are derived at ingest and stored as integers; dates are stored as gestational age plus study-relative offsets wherever a rule does not need a calendar date. The linkage back to identity stays in the EDC, under existing study controls.

Source documents are the exception, since scanned ultrasound and delivery records carry identifiers. These go to a separate encrypted store with tighter roles, automatic redaction on upload where a template is known, and access logged per view.

21 CFR Part 11 electronic signatures

  • Unique attribution. Entra ID SSO, MFA enforced, no shared accounts, no delegated signing. Ever.
  • Step-up authentication at signing. Re-authenticate at the moment of signature, not just at session start.
  • Signature manifest. Printed name, signed date-time with timezone, and the explicit meaning of the signature, rendered on screen and in the PDF.
  • Record locking. On signature the review becomes immutable and its content hash is bound into the signature row. Any later change is an amendment with its own signature.
  • Hash-chained audit. Each audit event stores the previous event's hash. Tampering breaks the chain and is detectable by a scheduled verifier job.
  • Validation. IQ/OQ/PQ with traceability from user requirements to test cases, plus a CSV summary report filed to the TMF. The rules engine gets its own test suite of adjudicated reference cases as PQ evidence.

Blinding & independence

Reviewer B must not see Reviewer A's answers, identity, or narrative edits until both are submitted. Enforce this at the query layer, not the UI layer, so an API call cannot leak what the screen hides. Treatment arm and, where the committee charter requires it, site are masked throughout.

Common failureBlinding implemented as a hidden div. Test it with the network tab open.

Data residency follows the study agreement and Zimbabwe's Data Protection Act alongside GDPR for EU-linked processing: a DPIA before go-live, documented lawful basis, and retention aligned to the trial's 25-year archive obligation. The AI endpoint must be contractually zero-retention with no training on submitted content, and deployed in the same region as the primary data store.

On the existing SharePoint portal

The OAC SharePoint portal in configuration today is the right interim answer and should still go to UAT: it gets adjudications flowing and teaches you the real field list. It is not the target. Treat it as the phase-zero data source and plan a one-way migration of its adjudications into this schema.

08

Phasing & open risks

Phase 0
now

Ship the SharePoint portal to UAT

Get adjudications flowing and lock the real field list. Everything learned here becomes the requirements baseline, and its records migrate in later.

Phase 1
~10 wks

Canonical store, LIS and EDC connectors, criteria engine

No UI beyond a data manager console. Prove the engine against 30 already-adjudicated reference cases and measure agreement. If the engine cannot beat the reference set, nothing downstream matters.

Phase 2
~8 wks

Adjudicator workbench, dual review, signatures

Queue, review, decision, Part 11 signing, PDF export. Run in parallel with the existing process for one cohort before cutting over.

Phase 3
~6 wks

Narrative generation and committee dashboard

AI comes last on purpose. It is the least essential component and the one that needs the most trust already banked.

Phase 4

Validation package and second endpoint

IQ/OQ/PQ, CSV report to the TMF, then prove extensibility by authoring a neonatal outcome rule set with no code changes.

What could sink this

DataSource coverage is unknown. If the LIS cannot push HL7 and ultrasound reports are scanned PDFs, "automatic aggregation" quietly becomes "manual abstraction with extra steps." Audit actual availability per site before committing to phase 1 scope.
ClinicalThe criteria set needs formal sign-off. ISSHP 2021 versus ACOG differ on proteinuria and on what counts as severe. The committee must ratify one, in writing, with a version label, before a single rule is coded.
RegulatoryAI in a regulated workflow needs a documented position. Even as draft-only prose, expect to justify it. Write the risk assessment now, not during an inspection.
ProcessBlinding and reviewer independence are a charter question, not a software question. Confirm whether B sees the same AI narrative A edited, or a fresh one. It changes the schema.
OpsBaselines are the silent failure. Renal and hepatic criteria depend on pre-pregnancy or early-pregnancy values that are often missing. Define the fallback rule explicitly rather than letting the engine return null.
Next decision

Pick the criteria set and confirm source availability per site. Both are prerequisites for phase 1 and neither needs an engineer.
